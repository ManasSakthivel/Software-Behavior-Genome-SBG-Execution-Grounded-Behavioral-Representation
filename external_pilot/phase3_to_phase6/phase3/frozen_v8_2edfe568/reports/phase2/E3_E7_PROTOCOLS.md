## 0. Common design

**Data.** The 321 development pairs built by the `experiments/v7b/k1_spike.py` task builders (`tasks_quixbugs`, `tasks_synthetic`, `tasks_bugsinpy`; synthetic selection seed 20261117, `MAXIN=12`, `SYN_MAX=150`). Arms and task counts: `quixbugs` 31 (buggy vs fixed), `quixbugs_neg` 85 (SP negatives of fixed), `synthetic` 150 (stratified v8 + v10_independent), `bugsinpy_units` 55 (of which the old run could not drive 9: class units / entry-policy failures, recorded as NOT_DRIVEN and scored as failed runs = abstention under SAP section 4). All data is NON-PRISTINE: V7-B was developed on these pairs. Every result is exploratory; no confirmatory claim, no generalisation claim, no OS-isolation claim, no tamper-proof claim.

**Truth labels** are never altered: they come from `scripts/build_dev_pairs_csv.py` (QuixBugs DIV = declared tests distinguish; synthetic = generator label; `SUSPECT_LABEL` and `UNLABELLED` excluded from primary denominators but counted). Old-engine reference counts (expected to be identical in E3 because truth does not depend on the engine): 321 pairs = DIV 106, NO_OBS_DIFF 152, UNLABELLED 57, SUSPECT_LABEL 6; primary-eligible 258; 101 projects (78 contain a DIV pair); the single `quixbugs` project holds 29 DIV and 84 NO_OBS_DIFF pairs (cluster-dominance caveat, section 8).

**Engine settings (all experiments).** `CFG = {"budget": {"cpu_seconds": 60, "per_run": {"cpu_s": 2, "wall_s": 5}}}` (k1_spike setting; all other keys at the `sbgv7/config.py` defaults: `r_det=3`, `r_replay=5`, `k_alt=3`, `s2_branch_floor=0.80`, `FOLD_FD1=True`), `OMP_NUM_THREADS=1`, `PYTHONHASHSEED=0` (child seed pinned by `isolation.DET_ENV`), 4 worker threads, inputs exactly as built by the k1_spike builders. Interpreter `.venv/bin/python` (CPython 3.13), macOS arm64.

**Statistics (all experiments, reuse `scripts/analyze_results.py` unchanged).** Unit of inference = project; percentile project-cluster bootstrap B=10000 (seed 42); two-sided project-level sign-flip permutation (exact if K<=16, else 20000 MC flips, seed 42); exact McNemar at pair level as sensitivity; Holm within family (primary family: false assurance and detection; secondary family: abstention, false alarm, labelled exploratory). Practical-significance rule from the SAP (D8): superiority needs Holm-adjusted p<0.05 AND lower 95% bound of improvement > +10pp (`meets_plus10pp`); smaller effects are "detectable but below the practical threshold"; a null is "inconclusive with CI", not "no effect". Failed/missing runs = abstention (ITT). Metric denominators (from `analyze_results.outcome_frame`): detection and false assurance over truth=DIV; false alarm over truth=NO_OBS_DIFF; abstention over all primary-eligible pairs (DIV + NO_OBS_DIFF).

**Run conditions.** (1) One experiment at a time; nothing else CPU-heavy on the machine (the per-run limits and the process-table test are load sensitive; a `resource_limit` verdict can be a load artefact). (2) Before each run: `git status` shows no change under `results/` (other than the new output dir) or `artifacts/`, output dir does not exist, record `git rev-parse HEAD`, `python --version`, `sw_vers`, `sysctl machdep.cpu.brand_string hw.ncpu hw.memsize`, the sandbox capabilities and the exact command in `RUN_RECORD.md` in the output dir. (3) The engine code (`sbgv7/`, `sbgv6/features.py`) must be identical across E1, E3-E7 (E7 checks the V6 digest). (4) Raw evidence is preserved; processed tables are regenerated by scripts, never edited. (5) Exclusions are only those stated below; any other exclusion is a protocol deviation to be listed.

Timestamps: `<ts>` = `YYYYMMDD_HHMMSS` of the run. E1 output (already running): `results/repro/p2_e1_20261118_074906/` (raw per pair at `raw/<arm>/run1|run2/<pair>/`, table at `proc/k1_spike_per_pair.jsonl`).

## E3. Post-fix detection, false assurance, abstention versus baselines

**Question.** On the 321 dev pairs, what are the current engine's detection, false-assurance and abstention rates versus B1 (plain differential), B1+rep (differential with repetition), B3 (coverage-guided mutator) and B4 (edit-size threshold)? B2 (declared tests) runs but has no truth role and is not in the CSV.

**Hypothesis.** Same exploratory direction as before: V7-B has lower false assurance than B1/B1+rep and does not have lower detection, at the cost of higher abstention. Direction only; no effect size assumed. The comparison against B3 and B4 has no directional hypothesis. The reduction may be mostly abstention (that is tested in E4).

**Dataset / arms.** All 321 pairs, arms as in section 0. Baselines run on the same inputs (read back from the spike's `inputs.json`).

**Command (as designed; documented, executed by the lead).** `scripts/run_evaluation.sh --full` writes `results/repro/full_<ts>/` and runs, in order: `pytest tests -q` (full legacy suite; any failure aborts the script by design), `k1_spike.py run --arms all --rerun 25`, `k1_spike.py summarize`, baselines run + summarize, `build_dev_pairs_csv.py`, `analyze_results.py ... --reference B1 --seed 42 --boot 10000`, `power_actual.py --test V7-B --reference B1`, `generate_figures.py`. Fallback if the pytest stage fails for a reason unrelated to the engine: record the failure in `RUN_RECORD.md`, then run the identical remaining stage commands with the script's exported environment; the failure is reported, not hidden. Estimated 40+ minutes.
Sensitivity (pre-declared, same as the old reference): rerun `analyze_results.py` on a CSV with rows of `flag=renamed_entry_SP-2` removed, into `statistics/sensitivity_excluding_SP2_renamed/`.

**Metrics.** Detection, false assurance (primary); abstention, false alarm (secondary); risk-coverage by minimum sufficiency (none/S1/S2/S3); class counts; per-project and per-dataset tables; cost (cpu_s median/max/sum); design statistics. Comparisons: V7-B, B1+rep, B3, B4 versus reference B1. Holm family = 4 comparisons x 2 primary outcomes. B1+rep versus V7-B is read from the same paired table (descriptive).

**Decision rules (fixed now).** (a) Headline claim "V7-B improves on B1" only if `meets_plus10pp` is true for false assurance or for detection; otherwise the wording is "not shown at +10pp on non-pristine data" with the CI. (b) A decrease in detection (V7-B below B1 with Holm p<0.05) is reported as a harm regardless of the false-assurance result. (c) Any V7-B abstention rate difference is reported alongside, never netted into a single score.

**Consistency check of V7-B verdicts (mandatory, run right after E3).**
1. E3 versus E1 run1 (same engine, same config): `p2_consolidate.py consistency --a E1/proc/k1_spike_per_pair.jsonl --b E3/processed/k1_spike_per_pair.jsonl --strict` compares (verdict, level, primary, secondary, witness_id) per pair. Expectation: identical. Fixed reading: "reproducible" only if at most 3 of the pairs differ at verdict level (about 1%), each difference listed with its reason code; all differing pairs are reported and none excluded. Differences concentrated in `resource_limit` / budget stops are labelled load-sensitivity, not engine nondeterminism, only if the E1/E3 run records show concurrent load; otherwise they are a finding.
2. E3 versus `results/postfix` (old engine, loose key: verdict, level, primary): descriptive transition matrix only. Changes are expected (MB-01/02/07/09/12, D-01..D-09 per the rerun matrix) and are not failures; no old number is cited as a measurement of the current engine.

**Verification.** E7 replays every E3 evidence directory. **Output** `results/repro/full_<ts>/` (alias "E3" in the consolidated report).

## E4. Ablations

**Question.** Which engine components change verdicts, and is the false-assurance reduction versus the ungated baselines explained by more INSUFFICIENT?

**Hypotheses (direction only, no magnitude, none assumed material).** V1 (`r_det=1`): fewer QUARANTINED/`nondeterministic` abstentions, detection and false alarm not lower. V2 (`r_replay=1`) and V3 (`k_alt=0`): fewer witnesses rejected as intermittent/control-sensitive, so detection and false alarm not lower, INSUFFICIENT not higher. V4 (all confirmation machinery off): same direction as V1-V3, largest. V5 (`FOLD_FD1=False`): fd-1 output ignored, so detection not higher, false assurance not lower. Whether the false-assurance reduction is "largely abstention" is stated as a hypothesis only; it is tested, not assumed.

**Dataset.** The same task list as E3 (imported builders; k1_spike untouched), all 4 arms, run1 only (no determinism reruns). Truth/dataset/flag copied from E3's V7-B rows.

**Variants (exact).** Config deltas on top of `CFG`, executed by `python -m sbgv7 compare` per pair via `experiments/v7b/p2_variants.py`:
V0 full (no delta); V1 `repeat.r_det=1`; V2 `repeat.r_replay=1`; V3 `repeat.k_alt=0`; V4 `r_det=1, r_replay=1, k_alt=0` (confirmation machinery off); V5 V0 config with `sbgv7.runner.FOLD_FD1=False` set by `python -c "import sys, sbgv7.runner as r; r.FOLD_FD1=False; from sbgv7.__main__ import main; sys.exit(main(sys.argv[1:]))" compare ...`.
**Sufficiency-gate ablation is NOT executed.** It is a DERIVED counterfactual computed from V0 evidence (and cross-checked with E3's V7-B rows), always labelled "derived, not executed": G_A re-labels every INSUFFICIENT as NO_DIVERGENCE_OBSERVED (S0); G_B re-labels only INSUFFICIENT whose primary reason is attributable to the sufficiency gate (`changed_region_not_activated, budget_exhausted_s0, blind_spot_dominant, unobservable_outcome`) and keeps engine/environment failures (e.g. `import_error`, `unsupported_signature`, `resource_limit`, `nondeterministic`, `tool_error`) as abstentions. Reported: detection, false assurance (count and rate), false alarm, abstention, false assurance among NO_DIVERGENCE_OBSERVED verdicts. Caveat: accounting identity only; it assumes nothing else changes.
**Ungated reference.** B1 and B1+rep rows from E3 (no rerun), on the same pairs.
**Abstention-attribution analysis (derived from E3).** Among DIV pairs where B1 (and separately B1+rep) says NO_DIFF (a false assurance), the distribution of V7-B verdicts; abstention share = INSUFFICIENT / (INSUFFICIENT + DIVERGENT_OBSERVABLE) with a project-cluster bootstrap CI.

**Metrics.** Verdict and level counts per variant; pair-level flips versus V0 on the category (verdict, level) and on verdict alone, with transition matrix; detection, false assurance, abstention, false alarm with CIs; paired comparisons versus V0 (CSV 1: V0-V5, reference V0, own Holm family of 5 x 2); ungated-reference CSV 2: V0, B1, B1+rep with reference V0 (separate Holm family, descriptive). In the ablation context the `meets_plus10pp` flag reads "the ablated variant beats the full engine by 10pp" and is reported only as that.

**Decision rules (fixed now).** Component classification per metric: NO_EFFECT_OBSERVED = zero category flips; SMALL = flips but Holm p>=0.05; DETECTABLE = Holm p<0.05 (either direction); reaching 10pp is stated only when the SAP rule holds. "The false-assurance reduction is largely abstention" is claimed only if the abstention share's lower 95% bound is > 0.5; "largely detection gain" only if its upper bound is < 0.5; otherwise "not established". No variant is chosen or tuned on these results.

**Commands (sequential, one at a time).**
```
E3=results/repro/full_<ts3>; E4=results/repro/p2_e4_<ts>; mkdir -p $E4/statistics
for V in V0 V1 V2 V3 V4 V5; do OMP_NUM_THREADS=1 PYTHONHASHSEED=0 .venv/bin/python experiments/v7b/p2_variants.py run --variant $V --out $E4/$V | tee $E4/$V.log; done
.venv/bin/python experiments/v7b/p2_variants.py csv --e3 $E3 --runs V0=$E4/V0 V1=$E4/V1 V2=$E4/V2 V3=$E4/V3 V4=$E4/V4 V5=$E4/V5 --out $E4/statistics/e4_ablation.csv
.venv/bin/python scripts/analyze_results.py $E4/statistics/e4_ablation.csv --out $E4/statistics/ablation --reference V0 --seed 42 --boot 10000
.venv/bin/python experiments/v7b/p2_variants.py csv --e3 $E3 --runs V0=$E4/V0 --baselines B1,B1+rep --out $E4/statistics/e4_ungated.csv
.venv/bin/python scripts/analyze_results.py $E4/statistics/e4_ungated.csv --out $E4/statistics/ungated --reference V0 --seed 42 --boot 10000
```
**Output** `results/repro/p2_e4_<ts>/{V0..V5}/{raw,proc,variant.json}`, `statistics/`. **Verification:** V0 per-pair verdicts must equal E3 V7-B (same consistency rule as E3, strict key); V1-V5 evidence is verifiable with `sbgv7 verify` (optional extra E7 source).

## E5. Sensitivity of `suff.s2_branch_floor`

**Question.** Do conclusions depend on the S2 branch-coverage floor?

**Expectation (direction).** In `decide.py` the floor only separates S1 from S2 inside NO_DIVERGENCE_OBSERVED (INSUFFICIENT iff a blocker; the floor is not a blocker). So: the S2 share is non-increasing in the floor (0.6 >= 0.8 >= 0.9), while verdict values, detection, false assurance and abstention are expected to be IDENTICAL across floors. A non-identical verdict value across floors would be an engine finding (or load artefact), not a hypothesis confirmation.

**Floors (fixed in advance, no retrospective selection or additions):** 0.6, 0.8, 0.9. 0.8 is the default but is run SEPARATELY as variant `S2F08` (explicit config) for independence from V0/E3. Same tasks, same inputs, run1 only, 4 workers.

**Metrics.** Verdict distribution; S1/S2 shares of NO_DIVERGENCE_OBSERVED verdicts; detection, false assurance, abstention at each floor (project-cluster CIs); risk-coverage rows (min sufficiency none/S1/S2) per floor; pair-level flips of (verdict, level) versus S2F08, and of verdict alone (expected 0); paired comparisons of each floor versus B1 (CSV with S2F06, S2F08, S2F09, B1, B1+rep, reference B1, one Holm family) and floors versus S2F08 (reference S2F08).

**Decision rules (fixed now).** "Headline stable" iff for each floor the sign of the V7-B-minus-B1 difference and the `meets_plus10pp` flag for detection and false assurance equal those at 0.8; otherwise "floor-sensitive" with the offending floor named. S2 share reported as a monotone check; non-monotone = finding.

**Commands.**

## E6. Runtime and resource cost

**Question.** What do replay/alt/determinism runs cost relative to the baselines, per input and per verdict class, and how variable is that cost?

**Hypothesis (direction only).** V0 uses more runs, CPU and wall time per pair than B1+rep, which uses more than B1 (V0 executes r_det, replay and alt runs in addition). No overhead size assumed; overhead is reported, not minimised. No hypothesis on peak RSS.

**Part A, derived from E3/E4 records** (`scripts/p2_e6_runtime.py records --src E3=... V0=...`). Collected quantities only: per-Run-record `meta.cpu_s` and `meta.wall_s` summed per pair and by `run_kind` (primary/repeat/replay/alt/probe), run counts, `verdict.json` `cpu_seconds_spent` (child CPU + parent thread CPU), process wall (`k1_spike_per_pair.jsonl wall_s`, measured under 4 concurrent workers, hence load-inflated), baseline `cpu_s`. **Per-run peak RSS is NOT stored in the evidence log** (isolation measures it but `runner.py` does not record it): none is reported from E3/E4. Tables: median/IQR/max/sum per system and arm, runs per verdict class, share of child CPU by run kind.

**Part B, dedicated sequential timing study.** Fixed 40-pair subset: runnable (non-skipped) k1_spike tasks sorted by (arm, pair); `random.Random(20261118).sample` per arm with quotas quixbugs 8, quixbugs_neg 8, synthetic 16, bugsinpy_units 8 (list printed by `p2_e6_runtime.py select`). `WORKERS=1` (one process at a time, nothing else running). Systems: V0 (`python -m sbgv7 compare`), B1 and B1+rep (each in its own fresh Python process via the script's internal `_one`, same CFG, same inputs, same 60 CPU-s cap). 5 repetitions; the 600 (rep, pair, system) jobs are shuffled with fixed seed 20261119 so drift is spread across systems. Measured per job with `os.wait4`: wall (perf_counter around the process), tree CPU (ru_utime+ru_stime, includes waited descendants), peak RSS (`ru_maxrss`, max over the waited tree, NOT additive), plus V0's engine-reported `cpu_seconds_spent`. Interpreter and import start-up are included for all systems; 5 import-only start-ups of `sbgv7.runner` and `sbgv7.baselines.baselines` are reported separately. Hardware (CPU brand, ncpu, memory, macOS version, Python, load average at start and end, power state) is stored in the summary. Estimate: roughly 30-45 minutes.
Statistics: per-pair median over reps; across pairs median/IQR/max/sum; relative overhead per pair = V0 median / baseline median (wall and CPU), reported as median/IQR of the ratio, ratio of sums and a project-cluster bootstrap 95% CI of the median ratio (seed 20261118, 10000 resamples); variability = coefficient of variation across the 5 reps per pair, reported as median and max.
**Decision rules (fixed now).** Overhead claim ("V0 costs more than B1") only if the CI of the median ratio excludes 1. A study with load average above 1.5 at start or end, or any failed job (rc != 0), is flagged and repeated once; both runs are kept and reported. Nothing is tuned.

**Commands.**
```
E6=results/repro/p2_e6_<ts>; mkdir -p $E6
.venv/bin/python scripts/p2_e6_runtime.py records --src E3=$E3 V0=$E4/V0 --out $E6/records.json
.venv/bin/python scripts/p2_e6_runtime.py select --out $E6/subset.json
.venv/bin/python scripts/p2_e6_runtime.py timing --out $E6/timing --reps 5
```
**Output** `results/repro/p2_e6_<ts>/`.

## E7. Evidence replay and corruption suite

**Question.** Does `python -m sbgv7 verify` recompute every recorded verdict, and does it detect (only) the documented classes of corruption?

**Expectation.** Part A: 100% exit 0 on every evidence directory of E3 (run1 and run2) and E1 (run1 and run2); any non-zero exit is an engine/verify bug to be reported with its directory, never excluded. (Exit 4 is expected only for size-cap omissions, which are not expected on this data.) Part B: exit codes as fixed below.

**Part A.** Every directory under `E3/raw/k1_spike` and `E1/raw` holding both `evidence.jsonl` and `verdict.json` (baseline directories are excluded: they hold no EvidencePackage/Verdict). Table: exit code x verdict class (DIVERGENT_OBSERVABLE; NO_DIVERGENCE_OBSERVED/S1; NO_DIVERGENCE_OBSERVED/S2; INSUFFICIENT per primary reason) per source. Verify must run on the same commit and V6 digest as the runs (the verifier checks it).

**Part B, corruption suite** on COPIES inside `E7/corruption/<class>/<case>` (originals untouched), against the first (sorted) passing directory of each class DIVERGENT_OBSERVABLE, NO_DIVERGENCE_OBSERVED and INSUFFICIENT. Expected exit codes (fixed here; `EXPECT` in `scripts/p2_e7_verify.py`):

| case | expected |
|---|---|
| flip one byte in a Run record | 1 |
| truncate log: drop last record (Verdict) | 1 |
| truncate log: cut mid-line | 1 |
| delete a middle record (chain unrepaired) | 1 |
| remove the EvidencePackage (chain repaired, log_head updated) | 1 |
| break the hash chain (alter a prev) | 1 |
| change verdict.json verdict value | 1 |
| change verdict.json log_head | 1 |
| delete evidence.jsonl | 2 |
| replace a source by `src_omitted` (size-cap simulation, chain repaired) | 4 |
| negative control: timing edit without chain repair | 1 |
| KNOWN LIMITATION: edit Run meta cpu_s/wall_s, rechain + update log_head | 0 (not detected) |
| KNOWN LIMITATION: edit Run summary status/detail ("taken as recorded"), rechain + update log_head | 0 (not detected) |
| KNOWN LIMITATION: delete verdict.json (optional for verify) | 0 (not detected) |

The forge-and-rechain cases are expected to pass verification: a writer who can recompute the chain and the pinned `log_head` yields a consistent log (documented in `sbgv7/verify.py`); recorded as a known limitation, not a failure. Deviations from the table are findings, reported as observed; the table is not adjusted afterwards.
Decision rule: E7 passes iff Part A is 100% exit 0 and Part B detects every case marked 1/2/4 with the expected code.

**Command.** `.venv/bin/python scripts/p2_e7_verify.py run --out results/repro/p2_e7_<ts> --src E3=$E3/raw/k1_spike E1=results/repro/p2_e1_20261118_074906/raw --workers 2` (about 1400 verify subprocesses, minutes). **Output** `results/repro/p2_e7_<ts>/{verify_results.jsonl,verify_table.json,corruption_results.json,corruption/}`.

## 8. Anticipated limitations
1. Non-pristine data; V7-B was shaped by these pairs; no confirmatory or generalisation claim.
2. Cluster dominance: all QuixBugs pairs are one project (29 DIV, 84 NO_OBS_DIFF); synthetic pairs are clustered by base program; many singleton clusters. Bootstrap and sign-flip are exploratory; K5 gates (60 projects, 250 adjudicated divergent pairs, kappa >= 0.7) are not met.
3. Load sensitivity: per-run limits (2 CPU-s, 5 s wall) and the 60 CPU-s budget make `resource_limit` and budget stops timing dependent; E4/E5 run 4 workers like E3 for comparability, E6 part B isolates timing at 1 worker. A single machine, no thermal control.
4. macOS only; `rlimit_as` and `rlimit_nproc` UNAVAILABLE per E1's capability record; no OS-isolation claim.
5. Hash seed pinned (0): hash-order sensitivity is untested (E2 not run).
6. The sufficiency-gate ablation is derived accounting, not an executed ablation; the G_B reason list is a judgement fixed in advance.
7. Peak RSS is not recorded in evidence; E6 part A reports none; part B's `ru_maxrss` is a tree maximum, not a sum.
8. Truth labels are generator-/test-based, with suspect and unlabelled pairs excluded (63 in the old reference); BugsInPy units have no truth and enter only as abstention accounting.
9. E7 tests detection of specific corruptions, not tamper-proofness; re-chained forgeries pass by design.
10. `run_evaluation.sh --full` begins with the full pytest suite; its failure aborts E3 (see fallback). Baselines B3/B4 use development rows for tuning (B4 threshold) and are descriptive.
11. Several V1-V4 verdict changes may be run-order or load artefacts; the strict E3-versus-V0 consistency check bounds that noise.
