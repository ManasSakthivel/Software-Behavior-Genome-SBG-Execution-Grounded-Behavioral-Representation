# Related Work

This chapter positions SBG against published work on comparing the behaviour of two program versions. It is a targeted literature review by a single reviewer, not a systematic review, and it does not follow PRISMA. Of the works cited, eight were read in full text by the reviewer, a further dozen recent ones were read through a summarising tool on their arXiv HTML pages, and the rest at abstract or metadata level; where a statement about a work depends on an abstract or a tool-processed text, the sentence says so. We report published results as the authors reported them. We did not run any third-party tool, and nothing here supports a claim that SBG outperforms any cited work.

## 1. Comparing versions by execution

Differential testing, in the sense of contrasting two versions of a system, was formulated for change detection by Evans and Savoia \cite{evans2007}. They generated characterisation tests for both the original and the modified system, ran each suite on both, and partitioned the outcome into preserved, regressed and progressed behaviours. In a preliminary study on three versions of one parser project with 38 seeded faults, the approach found 21%, 34% and 21% more behaviour changes than regression testing alone. The same paper states the limit that matters most for our purpose: if the set of differing tests is empty, "the result is ambiguous", because it can mean that the versions are identical or that the generated suites cannot tell them apart \cite{evans2007}. The statement is a threat to validity rather than a defined outcome, but it shows that the problem SBG addresses was recognised at the start of this line of work.

Later work in the same family includes behavioural regression testing \cite{jin2010automated}, regression unit-test generation with DiffGen \cite{taneja2008diffgen}, differential regression testing of REST API versions \cite{godefroid2020differential}, and differential testing with over-approximate symbolic execution \cite{rutledge2022automating}. We had access only to metadata or abstracts for most of these, so we do not characterise their outcomes beyond what those records state. Cross-implementation differential testing, in which several programs for one specification act as mutual oracles, is a neighbouring tradition \cite{petsios2017}. General surveys of the oracle problem and of regression testing provide background \cite{barr2015oracle,yoo2012regression}; we read only their metadata. Metamorphic testing replaces the second version by relations over inputs of one version \cite{segura2016,chen2018}; it is an alternative oracle, not a version-comparison method, and we do not discuss it further.

## 2. Symbolic, static and proof-oriented approaches

Shadow symbolic execution \cite{cadar2014shadow,palikareva2016,kuchta2018} merges old and new code with annotations, runs both in one symbolic execution in lockstep, generates a test at each point where the versions diverge, and replays divergent inputs natively on both versions. The motivating observation in its abstract is directly relevant here: tests written to cover a patch often exercise the same behaviour in the old and the new code \cite{palikareva2016}. On 18 Coreutils patches from CoREBench \cite{bohme2014corebench} the technique exposed some regression bugs and two bugs not recorded in the benchmark. The authors report code-level divergences separately from observed output differences, and list limits that include hand-written annotations, bugs needing file-permission or floating-point modelling, short timeouts, dependence on the starting test inputs, output-only difference detection, and non-determinism in the replay infrastructure and in their automatic classification \cite{palikareva2016}. We read the ICSE paper in full; the journal version \cite{kuchta2018} was available to us only as an abstract. Shadow solves a problem SBG does not attempt, namely generating inputs that reach new behaviour; SBG observes rather than solves.

Earlier symbolic frameworks, differential symbolic execution \cite{person2008} and directed incremental symbolic execution \cite{person2011}, characterise change effects over path conditions; we read only metadata and an abstract for them. Regression verification \cite{godlin2009,godlin2013} and its automation \cite{felsing2014} aim at proofs of equivalence of related programs. In the automation paper, which we read in full, evaluation programs are of 16 to 53 lines and handle integer variables only. SymDiff \cite{lahiri2012} and client-specific equivalence checking are verifier-based. These approaches define the "sound bar" and are the reason a dynamic tool must not word its outputs as equivalence.

DiffKemp \cite{malik2021,malik2026diffkemp} is the most relevant static neighbour. It compares functions of two versions of large C projects compiled to LLVM IR, using pattern-based transformations and synchronisation points. It reports equal, non-equal and "could not be determined"; in the full text we read, the third class arises typically when a function definition is not found, and the authors treat non-equal results as possibly false non-equalities. On Red Hat kernel releases the compared function sets run to hundreds of functions per release pair, with a few to a few dozen undetermined, in minutes per pair \cite{malik2021}. The journal extension adds global variables \cite{malik2026diffkemp} (abstract only). DiffKemp is therefore prior art for a conservative, non-binary verdict; its undetermined class reflects analysability, not the adequacy of observation.

Change-impact analysis supplies a further family. Chianti determines affected tests from static call graphs \cite{ren2004}; dynamic approaches use whole program paths or coverage \cite{larus1999whole,law2003,orso2003}. The authors of the full-text papers we read state that dynamic impact estimates hold relative to the executions observed \cite{law2003}. These works produce impact sets, not verdicts about output equality, and define no abstaining outcome. Daikon-style invariants \cite{ernst2001} can be computed per version and compared, but the authors note that accuracy depends on the quality and completeness of the test cases.

## 3. LLM-based differential and regression testing, 2024 to 2026

The most active recent line generates the comparing tests with large language models. We summarise the works we could verify, with the caveat that most are preprints and that we read them through a summarising tool.

Mokav \cite{etemadi2024mokav} searches for a difference-exposing test for two Python programs given an example test on which they agree, using execution feedback in an iterative LLM loop. On 32 QuixBugs pairs and 1,535 Codeforces-derived pairs its authors report success on 100% and 81.7% of pairs, against 4.9% for Pynguin and 37.3% for a prompting baseline on the larger set. Failure is reported only as exhaustion of the iteration budget, and the subjects are program pairs, not repository changes.

Testora \cite{pradel2025testora} targets real pull requests: it generates tests for the changed functions, runs old and new commits, re-executes differences to validate them, and asks an LLM to judge whether each difference agrees with the stated intent of the change. On four Python libraries (525 checked pull requests) its author reports 19 regression bugs and 11 unintended but beneficial changes, with 11 of 13 reported regressions confirmed by developers; the classifier reaches an F1 of 60% in its default configuration on 164 labelled entries. The output is binary (unintended or intended). Differences are re-executed and a classifier question asks whether a difference is deterministic. Diff coverage is measured, but as described it is not a precondition of an answer.

DiffTestGen \cite{hu2026difftestgen} directs generation at changed code through call-graph entry points and a "union coverage" feedback metric, defined as covered changed lines in old plus new over all changed lines. On 463 pull requests from two datasets it exposes behavioural differences in more pull requests than Testora on Testora's own data, according to its authors (79.7% against 77.1% in the body of the preprint; the abstract reports 78.2% overall, which we could not reconcile). Tests whose result changes on re-execution are discarded as flaky. A pull request with no difference is simply not counted as detected. PatchGuru \cite{leCong2026patchguru} infers executable "patch oracles" from the natural-language artefacts of a pull request; on 400 pull requests it reports precision 0.62 against 0.32 for Testora. In the text we read, an empty report does not distinguish "no inconsistency found" from an exhausted budget. ORION \cite{fu2026orion} separates behaviour to preserve from behaviour meant to change and evaluates on a balanced 154-pull-request benchmark against Testora, PatchGuru and general coding agents. It sends cases that fail for infrastructure reasons to human review rather than treating them as evidence.

Cleverest \cite{liu2025evaluating}, for programs with structured inputs such as parsers and interpreters, measures whether a commit is reached by coverage tooling and ranks outcomes in an ordinal scale of bug triggered, output changed, commit reached, and none. It is evaluated on 72 commits in eight programs against a directed greybox fuzzer. This ordinal result already distinguishes "reached but unchanged" from "not reached", although it serves as feedback for generation. DiffSpec \cite{rao2024diffspec} applies LLMs to differential testing of implementations of one natural-language specification (eBPF runtimes and WebAssembly validators) and notes that a differentiating test need not indicate a bug.

Two further 2026 preprints test whether a version comparison can be trusted when a difference is absent. Prefactory \cite{bouzenia2026prefactory} validates LLM-proposed refactorings with a differential test script whose outcomes are pass, fail and inconclusive, the last meaning that the script cannot run reliably; the authors state that a pass is evidence on the generated inputs, not proof of equivalence. SemaDiff \cite{ayub2026semadiff} classifies a Java commit as semantic-preserving only if all generated tests agree on both versions; on 183 labelled commits it reports 100% precision and 58.89% recall, and the authors note that exposing a change is harder than confirming its absence. Studies of generated tests point the same way: when LLMs regenerate tests after semantic-altering changes, over 99% of the failing tests pass on the original program while executing the altered region, which the authors read as tests tracking the original behaviour \cite{haroon2026evaluating}, and 8.4% to 16.9% of generated regression tests in one study encode faulty behaviour, with most such tests persisting through later changes \cite{charoosaei2026risks}.

## 4. Witnesses

In software verification, witnesses are exchangeable artefacts that an independent validator can re-check \cite{beyer2022verification,beyer2015witness,beyer2016correctness}. In cross-version testing the corresponding artefact is typically an executable test: Shadow's divergent inputs replayed on both versions \cite{palikareva2016}, Mokav's test asserting different outputs \cite{etemadi2024mokav}, Testora's test with both outputs and an explanation \cite{pradel2025testora}, PatchGuru's comparison program with runtime assertions \cite{leCong2026patchguru}. We did not find, in the works we could access, a common record format that covers both difference and no-difference outcomes together with the observation context (what was exercised, in which environment, under which seeds). That is an absence claim bounded by our limited search.

## 5. Whether the change was exercised: coverage, adequacy and observability

Patch coverage is studied as a property of test suites. Hilton et al. study coverage evolution over 7,816 builds of 47 projects, noting that coverage of a patch is used as a review signal \cite{hilton2018a}; Covrig and its ten-year follow-up analyse code, test and coverage co-evolution in mature C and C++ projects \cite{marinescu2014covrig,bailey2025code}; KATCH and test-suite augmentation generate tests to cover patches \cite{marinescu2013katch,santelices2008testsuite}. We read only abstracts or metadata for these. Cross-version testers use change coverage operationally, as seen above, but in the works we read it drives generation or is reported in evaluation; none made it a recorded condition on the outcome.

Coverage as evidence of testing strength is contested. Coverage is reported not to be strongly correlated with test suite effectiveness (title and metadata only) \cite{inozemtseva2014coverage}, and mutants are an imperfect stand-in for real faults (in one study of 357 faults, 73% were coupled to mutants and 17% were not) \cite{just2014mut}. Reaching code is distinct from changing state and from the change being visible at an output, the distinction at the centre of the propagation-infection-execution view \cite{voas1992pie}, of checked coverage, which counts only covered code that influences an oracle \cite{schuler2011assessing,schuler2013checked}, and of coincidental correctness \cite{masri2010cleansing}; we read only snippets or metadata for these. Shadow's observation that tests covering a patch may still exercise the same behaviour \cite{palikareva2016} is the most direct published statement of the same caution in a cross-version setting. Any sufficiency level built on coverage of changed lines must be presented as a proxy, not as a measure of evidence strength.

## 6. Inconclusive outcomes and abstention

A non-binary outcome is not new. DiffKemp separates proven-equal, not-proven-equal and undetermined \cite{malik2021}; Prefactory has an inconclusive class \cite{bouzenia2026prefactory}; ORION routes infrastructure failures to review \cite{fu2026orion}; Cleverest's ordinal scale distinguishes reached from unreached commits \cite{liu2025evaluating}; and Evans and Savoia name the ambiguity of an empty difference set \cite{evans2007}. By contrast, Testora, DiffTestGen, SemaDiff and Mokav return binary results or "not detected", and the empty report of PatchGuru is not separated into cases in the text we read.

In machine learning, abstention is a developed field: the reject option dates to Chow \cite{chow1970on}, selective classification and surveys followed \cite{geifman2017,hendrickx2024machine}, and recent work applies abstention to language models and to code generation \cite{wen2025know,spiess2025calibration,jeong2025towards}. These methods abstain on model uncertainty or on test-based checks of generated code. We found none that abstains because a change to a program was not adequately observed (inference from abstracts). The established evaluation vocabulary, risk against coverage, is available to any tool that reports an insufficient outcome and should be used when reporting it.

## 7. Nondeterminism and flakiness

Flaky tests are well studied: empirical analyses and surveys \cite{luo2014an,parry2021a}, detection and classification \cite{lam2019idflakies,bell2018d,rahman2025flakylens}, and the nondeterminism of language models themselves \cite{ouyang2025an}. Inside cross-version testers, handling is ad hoc and recent: Testora re-executes differences \cite{pradel2025testora}, DiffTestGen discards tests whose results change on re-execution \cite{hu2026difftestgen}, Cleverest repeats runs and reports no observed flakiness \cite{liu2025evaluating}, and Shadow's authors state non-determinism in replay and in classification as a limit \cite{palikareva2016}. PatchGuru, SemaDiff and Prefactory describe no such handling in the text we read. Repetition to remove flaky differences is therefore established practice; what remains open is how nondeterminism evidence is recorded and how it shapes the verdict.

## 8. Equivalence and equivalent mutants

Equivalence of programs is undecidable in general, as stated in the abstract of the regression verification papers \cite{godlin2009,godlin2013} and in the study of equivalent-mutant detection cited below, and equivalent mutants are a long-standing problem in mutation testing \cite{budd1982two,madeyski2014overcoming} (metadata only for the latter two). Trivial compiler equivalence detects some equivalent mutants by comparing optimised code \cite{papadakis2015}; learned classifiers have been compared extensively, with the best fine-tuned model reaching an F1 of 86.58% against 50.8% for the compiler-based baseline on 3,302 Java mutant pairs \cite{tian2024large}, and LLMs have been benchmarked on judging equivalence of program pairs \cite{wei2025equibench}. All of these try to decide or approximate equivalence. A tool that records only observed divergences and the evidence behind an absence of divergence, and whose verdict set contains no equivalence value, is compatible with this literature but does not substitute for it. Execution traces are also used as model inputs \cite{ni2024next}; a recorded witness differs from a learned representation in being a re-checkable observation.

## 9. Evaluation practice and threats in this literature

The recent differential-testing studies share features that matter for evaluating a new tool. Most use Python pull-request benchmarks drawn from the same few libraries (keras, marshmallow, pandas, scipy) \cite{pradel2025testora,hu2026difftestgen,leCong2026patchguru}; labels are often assigned by one researcher; several authors note possible training-data exposure \cite{fu2026orion,etemadi2024mokav}; and a few papers contain internal inconsistencies between abstract and body figures. Methodological pitfalls from machine learning for software engineering apply: duplicates can inflate reported performance substantially \cite{allamanis2019}, label noise and leakage threaten validity, reproducibility depends on artefact sharing \cite{gonzalezbarahona2011on,timperley2021understanding,kapoor2023leakage}, and fuzzing evaluations need repeated runs and statistical care \cite{klees2018evaluating}. Studies in this literature also use differing baselines, from none to coding agents, so their reported numbers are not comparable with each other (inference).

## 10. Positioning of SBG

SBG compares two versions by executing both, and its design contributions are four, each qualified by the prior art above.

First, SBG records its evidence as replayable records, covering outcomes with and without a difference. Executable witnesses are established in testing and verification; we found no single record that carries observation context for both outcomes, which is an absence claim from a limited search (C1).

Second, SBG records how much of the changed region was exercised and conditions the "no divergence observed" outcome on it. The measure of change coverage is not new, and several recent tools compute it \cite{hu2026difftestgen,liu2025evaluating,pradel2025testora}. What we did not find in the works read is its use as a recorded condition of the verdict (C2). Because coverage is a contested proxy, SBG's levels are not measures of correctness.

Third, SBG has an explicit insufficient outcome whose grounds are recorded evidence about the change. Three-way outcomes exist \cite{malik2021,bouzenia2026prefactory}, so the claim is limited to the grounds and to the guarantee that no equivalence outcome can be emitted (C3).

Fourth, SBG repeats executions and alternates environment controls to separate genuine from nondeterministic differences, and reports the result in the verdict. Repetition against flakiness is standard practice \cite{pradel2025testora,hu2026difftestgen}; any contribution is the typing of that evidence inside the verdict (C4).

SBG does not generate inputs to reach changed code, so it is not a competitor to Shadow or to the LLM generators in discovering divergences; it could consume their inputs. SBG's own evaluation is development-grade: it has used developer-owned or previously exposed benchmarks, no independent real-project benchmark has been completed, and its own red-team review found no measured benefit of the sufficiency gate or the replay machinery over simpler baselines on the data available. Those findings are not published results and are not evidence for or against the works cited here.

## 11. Limitations of this review

The search was known-item and gap-driven, not exhaustive; metadata was verified through Crossref, the arXiv interface and Semantic Scholar, and no records were screened by two reviewers. The ACM Digital Library was not accessible, so, for example, the journal version of Shadow was read only at abstract level. Twelve of the twenty full-text reads were through a summarising tool and did not cover the final portions of some papers, and 76 of 185 evidence records are metadata only. Several of the most relevant works are 2026 arXiv preprints that may change. Statements that a capability is absent from a work are therefore weaker than statements that it is present.
