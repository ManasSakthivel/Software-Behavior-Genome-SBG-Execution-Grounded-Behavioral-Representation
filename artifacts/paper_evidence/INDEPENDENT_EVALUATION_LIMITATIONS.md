# INDEPENDENT EVALUATION LIMITATIONS
**Branch:** `remediation/sbg-v4`

**Date:** 2026-10-30  
**Auditor:** Bob (research engineering agent)  
**Question:** Can a stronger independent evaluation be constructed that would satisfy the independence criteria stated in the task brief?

---

## 1. Current State of V10 Independence

The V10 evaluation uses 19 programs that were:
- Never seen during V8 or V9 training/development (excluded from V8 by token-Jaccard threshold 0.10–0.15).
- Never scored until a single frozen run after the freeze manifest was committed.
- Labelled by a dynamic oracle (EQ = base output; CH = oracle-confirmed output difference from SC mutation).
- Free of the SP-8/SP-11 label defects found in the development data.
- Evaluated with all baselines under identical conditions.

**Critical independence caveat:** The 19 programs are algorithmic siblings of development programs. They are drawn from the same generator (the same author, the same transformation families SP-1 through SP-12 and SC-1 through SC-13, the same input construction protocol). The token-Jaccard deduplication ensures no overlapping code, but it does not ensure that the programs test different capabilities of SBG. A scorer calibrated on a sorting-algorithm program will naturally generalise to other sorting-algorithm programs, even if the specific implementations differ.

**V10 is correctly described as a withheld test set, not as an independently authored or sourced evaluation.**

---

## 2. Requirements for a Stronger Independent Evaluation

The task brief specifies the following requirements:

1. Programs independently authored or sourced (not generated by the same system)
2. Documented provenance for each source program
3. Documented inclusion/exclusion protocol
4. Equivalent/behaviour-changing examples with independently validated labels
5. Defensible mechanism for establishing behavioural equivalence under the execution model
6. Overlapping edit-size distributions across CHANGED/EQUIVALENT classes
7. Frozen SBG implementation
8. Frozen baseline definitions and evaluation code
9. Prespecified primary metric and statistical analysis
10. Program-level uncertainty estimates
11. Record of all exclusions, failures, and unevaluated examples

Requirements 7–11 are already in place (frozen SBG V5, frozen evaluation code, documented procedures). The critical gap is requirements 1–6.

---

## 3. Why a Strongly Independent Evaluation Cannot Be Constructed Within Available Resources

### 3a. Source program availability

An independently authored evaluation would require Python programs whose implementations and transformations were not generated by the same pipeline. Potential sources:

**Option A: Public algorithm repositories (GitHub, LeetCode, HackerRank solutions)**  
- Available: Yes.  
- Problem: These programs are algorithmically similar to the existing benchmark (sorting, graph traversal, DP). SBG's discrimination capability may already be implicitly tuned to this programme domain via the weight and threshold selection on v9c train.  
- More fundamentally: constructing EQUIVALENT/CHANGED pairs from public programs still requires applying the same SP/SC transformation families (or equivalent), which would reproduce the generation artifact. Using different transformation families would test a different task.  
- **Verdict:** Could yield independent source programs, but would not constitute a genuinely orthogonal evaluation unless new transformation families are defined and validated.

**Option B: Open-source real-world Python projects**  
- Available: Yes (GitHub, PyPI).  
- Problem: Constructing controlled EQUIVALENT/CHANGED pairs from real-world code requires: (a) applying semantic-preserving and semantic-breaking transformations correctly to non-algorithmic code; (b) validating labels against a dynamic oracle; (c) ensuring input coverage (protocol inputs must exercise the relevant behaviour). Real-world functions often depend on class state, I/O, networking, or complex data structures that the current tracer does not handle.  
- Time estimate: Constructing a validated 200-pair dataset from real-world code would require 2–4 weeks of engineering work (harness, input generation, oracle validation, provenance documentation).  
- **Verdict:** Technically possible but not completable within the current task boundary.

**Option C: BugsInPy/QuixBugs as real-bug evidence**  
- Already attempted; results are below chance (see §5 of this report and REAL_BUG_GENERALISATION_AUDIT.md).  
- This constitutes a genuine test of independent generalisation with a negative result.  
- **Verdict:** Already the best available independently sourced evidence, and it is unfavourable.

**Option D: Synthetic programs generated by a different author or generator**  
- Would require a collaborator or a different automated generator.  
- Not available within the project.  
- **Verdict:** Not feasible without additional resources.

### 3b. Oracle validation without model access

The task brief requires "label validation performed without access to the model's scores." For a new dataset constructed by the same researcher, achieving this requires either:
- A second, independent researcher to validate labels, or
- An automated oracle that is demonstrably independent of SBG's scoring.

The dynamic output oracle used in V10 is independent of SBG (it checks program outputs directly). Any new evaluation using the same oracle mechanism would satisfy this requirement automatically. The gap is source program independence, not oracle independence.

### 3c. Edit-size distribution overlap

The V10 evaluation shows a residual edit-size confound: mean edit CH = 10.29, mean edit EQ = 8.36 (AUROC of forward edit = 0.616). The composed design reduces but does not eliminate this confound. A new evaluation on independently sourced programs would need to ensure overlapping edit distributions — which requires constructing or filtering pairs, again requiring significant engineering effort.

---

## 4. What V10 Does and Does Not Demonstrate

V10 **does** demonstrate:
- SBG V5 achieves AUROC 0.897 [0.863, 0.922] on 638 pairs from 19 programs withheld from training.
- The SBG V5 implementation and threshold generalise from training programs to withheld programs within the same generation family.
- Stratified AUROC (controlling for exact edit size) = 0.875, confirming some discrimination is not reducible to edit-size information.

V10 **does not** demonstrate:
- Generalisation to programs from a different author, generator, or domain.
- Generalisation beyond the specific SP and SC transformation families used.
- Generalisation to real codebases or real bug patterns.
- Performance on programs with different edit-size distributions.

---

## 5. Data and Resources Required for a Stronger Evaluation

To satisfy all requirements in the task brief, a stronger independent evaluation would require:

| Requirement | Minimum resource |
|---|---|
| Independently authored programs | 20–40 Python functions from public repositories, not algorithmically identical to existing benchmark programs |
| Controlled transformation pipeline | Implementation of SP/SC transformations for new code types, with correctness testing |
| Dynamic oracle with input generation | Input generation adapted to the new programs; oracle execution |
| Label validation | One automated pass + one manual spot-check by a second researcher |
| Provenance documentation | File-level provenance for each source program (URL, commit, license) |
| Estimated time | 3–6 weeks engineering + 1–2 weeks validation |

---

## 6. Recommendation for Paper

The paper should:

1. Describe V10 accurately as a withheld test set of algorithmic sibling programs, not as independently sourced programs.
2. Qualify the V10 generalisation claim precisely: "SBG V5 generalises to withheld programs drawn from the same generation procedure, achieving AUROC 0.897 [0.863, 0.922] on 19 programs (638 pairs) held out from all training and development."
3. Acknowledge that generalisation to programs from independent sources is **not demonstrated** and that the BugsInPy/QuixBugs evidence (a negative result on independently sourced programs) represents the strongest available test of cross-source generalisation.
4. Identify independent evaluation on real-world or third-party authored programs as explicit future work.

Do not describe V10 as proving that SBG generalises to independently sourced programs.

---

## Conclusion

A fully independent evaluation satisfying all requirements of the task brief **cannot be completed within the existing project resources and time boundary**.

The specific blockers are:
- No independently authored or sourced Python programs with controlled EQUIVALENT/CHANGED labels exist within the project.
- Constructing such a dataset from public programs would require 3–6 weeks of engineering and validation work.
- The best available independent evidence (BugsInPy/QuixBugs) provides a negative result.

The V10 evaluation is the best achievable within this project. It is scientifically sound as a withheld-programs evaluation, provided its independence limitation is clearly stated.

**This limitation does not prevent submission but constrains the generalisation claims that may be made.** The paper's contribution must be scoped to the benchmark setting with the acknowledged independence caveat. The absence of independent-source evaluation should be stated explicitly as a limitation and a direction for future work.
