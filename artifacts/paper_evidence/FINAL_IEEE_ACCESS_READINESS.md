## B. Main Contribution

SBG proposes and evaluates a structured execution genome representation for discriminating behaviour-changing from behaviour-preserving code edits under a fixed-input, output-free oracle. The central contribution is twofold: (1) the identification and quantification of edit-size confounding as a systemic validity threat in transformation-family-based benchmarks, and (2) a controlled evaluation showing that execution trace comparisons can discriminate behaviour-changing edits substantially above edit-size baselines on size-decoupled pairs (V10: AUROC 0.897 vs. 0.616 for edit size), with oracle-validated labels and pre-registered hypothesis tests. A null result for incremental value beyond execution statistics and a genuine generalisation limitation to real-bug scenarios are also documented honestly.

## D. Remaining Blockers

### Blocker 1: H4 Null Result — No Demonstrated Incremental Value Beyond Execution Statistics (HIGH SEVERITY)

**Why it matters:** If SBG adds nothing beyond execution statistics, the practical motivation for using it over simpler features is weakened. This is the central question reviewers will ask.

**Does it prevent submission?** No. A null result is scientifically valid. The contribution can be reframed around the benchmark methodology and the demonstrated edit-size independence, rather than claiming SBG is an additive predictor.

**Minimum work to resolve:** Adding ~40–60 more independent programs would narrow the H4 CI sufficiently to either detect a 0.03 AUROC improvement or confidently exclude it. This is estimated at 3–6 weeks of work and is not feasible within this project boundary.

**Alternative resolution:** Narrow the contribution claim. The paper can honestly say "SBG replaces edit + execution stats as a single predictor (AUROC 0.897 vs. 0.791) but does not demonstrate additive value when combined with them." This is a valid, defensible finding.

### Blocker 2: V10 Not Fully Independently Sourced (MODERATE SEVERITY)

**Why it matters:** Reviewers assessing generalisation will note that V10 programs are generated by the same procedure as development data.

**Does it prevent submission?** No. The paper must clearly state this as a limitation.

**Minimum work to resolve:** Constructing an independently authored evaluation dataset is estimated at 3–6 weeks and is not feasible within this project.

**Alternative resolution:** The paper must describe V10 as a "withheld programs" evaluation, not an "independent" evaluation. Use the BugsInPy/QuixBugs results as the available independent-source evaluation (negative result).

### Blocker 3: Real-Bug Generalisation Not Demonstrated (MODERATE SEVERITY)

**Why it matters:** IEEE Access reviewers and practical users will ask whether SBG is useful beyond synthetic benchmarks.

**Does it prevent submission?** No. The limitation is honest and documented. Papers can and should report genuine negative results.

**Minimum work to resolve:** A new real-bug experiment with bug-triggering inputs and without the output-free constraint would likely improve results but would test a different protocol. This is not feasible within this project.

**Alternative resolution:** State clearly as a limitation. The mechanism is understood (fixed inputs don't exercise most real bugs; output-free design hides return-value changes). This is a reasonable scope limitation for a methods paper.

### Blocker 4: Novelty Claim Must Be Precisely Bounded (LOW SEVERITY)

**Why it matters:** Overstating novelty will attract rejection.

**Does it prevent submission?** No. The contribution is novel in the specific combination described.

**Minimum work to resolve:** Careful related-work discussion citing Danglot et al. (DCI), Kessel & Atkinson, and the benchmark validity literature.

**Alternative resolution:** Frame contribution as (a) the confound identification and composed design, (b) the controlled quantitative evaluation with preregistered tests, (c) the null result for H4, and (d) the documented generalisation limitations. Avoid claiming "first use of execution traces for equivalence detection."

### Blocker 5: 19-Program Evaluation — Wide H4 CI (LOW SEVERITY)

**Why it matters:** The large between-program variance (H4 CI width ±0.07) limits inferential precision.

**Does it prevent submission?** No. This is a transparency issue, not a validity issue.

**Minimum work to resolve:** More programs (see Blocker 1).

**Alternative resolution:** Disclose the CI width, explain the between-program heterogeneity, and acknowledge that the current sample cannot support a precise conclusion about incremental value.

## E. Safe Abstract-Level Claims

The manuscript author may use the following claims without overstating the evidence:

1. "We identify edit-size confounding as a systemic validity threat in transformation-family-based behaviour-change benchmarks, and propose a composed design that partially decouples edit size from label."

2. "SBG V5, an execution genome representation, discriminates behaviour-changing from behaviour-preserving edits substantially above edit-size baselines on oracle-validated, composed pairs (V10: AUROC 0.897 [0.863, 0.922] vs. 0.616 for forward edit size; 19 withheld programs, 638 pairs)."

3. "SBG V5's discrimination persists when edit size is exactly controlled (edit-size-stratified AUROC 0.875)."

4. "Adding SBG V5 to an edit-size predictor improves AUROC by +0.25 [0.22, 0.29] on the withheld evaluation set."

5. "SBG V5 does not demonstrate statistically significant incremental value beyond edit size and execution statistics (H4: ΔAUROC = +0.006, CI [−0.069, +0.068])."

6. "The benchmark contains label defects (8.7% of EQUIVALENT training variants are mislabelled); oracle-validated labelling in V10 removes these defects."

7. "SBG V5 does not generalise to real bugs under fixed-input oracle conditions (BugsInPy: AUROC 0.497 [0.402, 0.596]; QuixBugs: 0.444 [0.355, 0.539])."

8. "Exact-zero SBG V5 scores predominantly correspond to EQUIVALENT pairs (79%) and are the correct output; the zero rate is not evidence of a scorer defect."

## F. Claims That Must Not Be Made

1. **"SBG is validated for real-world bug detection."** — BugsInPy and QuixBugs results are near chance; fixed inputs do not exercise most real bugs.

2. **"SBG provides incremental value beyond execution statistics."** — H4 fails in both independent evaluations. ΔAUROC = +0.006, p = 0.809 (V10).

3. **"V10 proves generalisation to independently authored programs."** — V10 programs are generated by the same author and procedure as development data.

4. **"V6 is superior to V5."** — H5 not rejected after Holm correction (p_adjusted = 0.090). V6 is experimental.

5. **"A high AUROC on synthetic pairs establishes practical utility."** — AUROC on a controlled synthetic benchmark does not imply utility for real-world change detection, which requires different inputs and may not use the output-free protocol.

6. **"SBG is the first dynamic analysis approach for program equivalence."** — Kessel & Atkinson (2019) and DCI (2020) predate this work.

7. **"The zero-score rate of 37% has been resolved."** — It has been explained (not a defect), but the representation limitation (output-free, fixed inputs, coarse abstraction) remains.

8. **"The H4 null result confirms that SBG and M_EX are equivalent in performance."** — The wide CI [−0.069, +0.068] does not rule out meaningful differences; the test is underpowered for small effects.

## G. Final Go/No-Go Decision

**GO — within a precisely bounded scope.**

The narrowest defensible scope for an IEEE Access submission is:

> *A controlled benchmark study of execution genome representations for behaviour-change detection, with emphasis on identifying and measuring edit-size confounding, oracle-validated label construction, and quantitative evaluation including a documented null result for incremental value beyond execution statistics.*

This scope excludes:
- Claims about practical real-world bug detection.
- Claims about independently authored program generalisation.
- Claims about additive value beyond execution statistics.

Within this scope, the paper is substantive, honest, reproducible, and addresses a genuine methodological problem in the software-change analysis literature. The primary positive results (H1, H2, H3) are supported; the negative results (H4, real-bug generalisation) are documented and informative.

The contribution is suitable for IEEE Access — a broad-scope, open-access journal — rather than a narrow top-venue paper claiming a breakthrough. The honest presentation of mixed results is compatible with IEEE Access standards.
