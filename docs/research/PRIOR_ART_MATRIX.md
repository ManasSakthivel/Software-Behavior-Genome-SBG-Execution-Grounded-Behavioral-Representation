## Reading Guide

Each entry follows this schema:

| Field | Meaning |
|---|---|
| **Citation** | Author(s), title, venue, year |
| **Year** | Publication year |
| **Problem** | Core research question addressed |
| **Representation** | How programs or behaviors are encoded |

## Domain 1 — Software Fingerprinting

### [1] Luo et al. — BinDiff (extended)
**Citation:** Luo, L., Ming, J., Wu, D., Liu, P., Zhu, S. "Semantics-Based Obfuscation-Resilient Binary Diffing with Applications to Software and Malware Plagiarism Detection." *IEEE TIFS*, 2017.  
**Year:** 2017  
**Problem:** Detecting binary-level code similarity despite compiler transformations and obfuscation.  
**Representation:** Input/output semantic summaries (symbolic execution over basic blocks) + control-flow graphs.  
**Analysis type:** Hybrid (static CFG extraction + dynamic symbolic execution per block)  
**Language scope:** Binary (x86/x64); language-agnostic at binary level  
**Benchmarks:** OpenSSL, libcrypto, custom obfuscated malware corpora  
**Metrics:** Precision, recall, F1 on plagiarism detection; matched-function rate  
**Limitations:** Does not scale to whole-program behavioral equivalence. Symbolic execution path explosion limits coverage. No inter-procedural semantics.  
**SBG delta:** SBG operates at source-level behavioral semantics across multiple languages; it is not restricted to binary diffing and tracks behavioral trajectories over time rather than pairwise similarity.

---

### [2] Pewny et al. — Cross-Architecture Bug Search
**Citation:** Pewny, J., Garmany, B., Gawlik, R., Rossow, C., Holz, T. "Cross-Architecture Bug Search in Binary Executables." *IEEE S&P*, 2015.  
**Year:** 2015  
**Problem:** Finding semantically equivalent vulnerable functions across different CPU architectures.  
**Representation:** I/O-based semantic summaries generated by random testing; cosine similarity over feature vectors.  
**Analysis type:** Dynamic (random input testing to generate I/O pairs)  
**Language scope:** Binary; cross-architecture (x86, ARM, MIPS)  
**Benchmarks:** Known CVEs in OpenSSL, libPNG across 4 architectures  
**Metrics:** Recall of known-vulnerable functions, ranking quality  
**Limitations:** I/O sampling may miss rare behaviors. No notion of behavioral change over versions. Only function-level granularity.  
**SBG delta:** SBG defines a "genome" as the full behavioral trajectory of a software artifact across its history, not just a per-function I/O summary.

---

### [3] Eschweiler et al. — discovRE
**Citation:** Eschweiler, S., Yakdan, K., Gerhards-Padilla, E. "discovRE: Efficient Cross-Architecture Identification of Bugs in Binary Code." *NDSS*, 2016.  
**Year:** 2016  
**Problem:** Scalable binary code search across architectures using structural and numeric features.  
**Representation:** Numeric feature vectors (CFG properties, instruction counts) + structural CFG matching.  
**Analysis type:** Static  
**Language scope:** Binary; cross-architecture  
**Benchmarks:** OpenSSL, libssh, Putty binaries across x86/ARM/MIPS  
**Metrics:** True positive rate at rank 1/5/10, scalability (query time)  
**Limitations:** Features are shallow; obfuscation breaks numeric features easily. No semantic content.  
**SBG delta:** SBG uses deep behavioral representations rather than surface-level CFG statistics.

---

### [4] Xu et al. — Neural Network-based Binary Code Similarity
**Citation:** Xu, X., Liu, C., Feng, Q., Yin, H., Song, L., Song, D. "Neural Network-based Graph Embedding for Cross-Platform Binary Code Similarity Detection." *CCS*, 2017.  
**Year:** 2017  
**Problem:** Learning embeddings for binary CFG blocks for cross-platform similarity.  
**Representation:** Graph neural network embeddings over CFG (Gemini model).  
**Analysis type:** Static  
**Language scope:** Binary; x86, ARM, MIPS  
**Benchmarks:** OpenSSL, Coreutils, 8 open-source projects  
**Metrics:** AUC, recall@k  
**Limitations:** Graph embedding is compiler-sensitive; does not capture runtime behavior. Training requires labeled pairs.  
**SBG delta:** SBG does not require labeled pairs of equivalent programs; behavioral signatures are extracted without supervision from execution traces.

## Domain 2 — Behavioral Fingerprinting

### [5] Bayer et al. — TTAnalyze
**Citation:** Bayer, U., Comparetti, P.M., Hlauschek, C., Kruegel, C., Kirda, E. "Scalable, Behavior-Based Malware Clustering." *NDSS*, 2009.  
**Year:** 2009  
**Problem:** Clustering malware samples by runtime behavior at scale.  
**Representation:** System-call n-grams and API call sequences recorded via full-system emulation.  
**Analysis type:** Dynamic  
**Language scope:** Windows PE binaries (language-agnostic at OS level)  
**Benchmarks:** 75,000 malware samples from antivirus feeds  
**Metrics:** Clustering quality (purity, NMI), scalability  
**Limitations:** System call sequences conflate benign OS noise with malicious behavior. Evasion-sensitive: malware can detect sandbox.  
**SBG delta:** SBG targets correctness/regression detection in known-good software, not malware triage. It builds longitudinal behavioral profiles across versions, not one-shot cluster assignment.

---

### [6] Moser et al. — Exploring Multiple Execution Paths
**Citation:** Moser, A., Kruegel, C., Kirda, E. "Exploring Multiple Execution Paths for Malware Analysis." *IEEE S&P*, 2007.  
**Year:** 2007  
**Problem:** Trigger-based malware hides behavior; explore multiple paths to expose it.  
**Representation:** Execution path tree via taint-guided branching.  
**Analysis type:** Dynamic (multi-path)  
**Language scope:** x86 Windows binaries  
**Benchmarks:** Manual case studies on trigger-based malware samples  
**Metrics:** Coverage of triggered behaviors (manual inspection)  
**Limitations:** Path explosion; no semantic abstraction above system calls.  
**SBG delta:** SBG is concerned with behavioral specification of correctness, not adversarial exposure.

---

### [7] Kinable & Kostakis — Malware Classification via CFG Clustering
**Citation:** Kinable, J., Kostakis, O. "Malware classification based on call graph clustering." *Journal in Computer Virology*, 2011.  
**Year:** 2011  
**Problem:** Classify malware families using structural similarity of call graphs.  
**Representation:** Call graph; graph edit distance.  
**Analysis type:** Static  
**Language scope:** PE binaries  
**Benchmarks:** 1,245 malware samples across 14 families  
**Metrics:** Classification accuracy, ROC AUC  
**Limitations:** GED is NP-hard; approximate only. Static call graphs miss dynamic dispatch.  
**SBG delta:** SBG uses dynamic call paths and can handle polymorphism/dynamic dispatch that static call graphs miss.

## Domain 3 — Dynamic Program Analysis

### [8] Cadar et al. — KLEE
**Citation:** Cadar, C., Dunbar, D., Engler, D. "KLEE: Unassisted and Automatic Generation of High-Coverage Tests for Complex Systems Programs." *OSDI*, 2008.  
**Year:** 2008  
**Problem:** Automatic test generation with high coverage using symbolic execution.  
**Representation:** Symbolic state (path conditions); constraint solver (STP).  
**Analysis type:** Dynamic (symbolic execution)  
**Language scope:** C/C++ via LLVM IR  
**Benchmarks:** GNU Coreutils (89 programs), BUSYBOX  
**Metrics:** Line coverage, branch coverage, bugs found  
**Limitations:** State explosion; limited to programs compilable to LLVM IR; solver bottleneck on complex arithmetic.  
**SBG delta:** SBG does not generate tests; it characterizes behavioral signatures from existing execution traces. KLEE's constraint-solver cost is avoided.

---

### [9] Godefroid et al. — DART / SAGE
**Citation:** Godefroid, P., Klarlund, N., Sen, K. "DART: Directed Automated Random Testing." *PLDI*, 2005. | Godefroid, P., Levin, M.Y., Molnar, D. "Automated Whitebox Fuzz Testing." *NDSS*, 2008.  
**Year:** 2005 / 2008  
**Problem:** Systematic whitebox fuzzing combining concrete and symbolic execution (concolic testing).  
**Representation:** Concrete + symbolic execution; path constraints.  
**Analysis type:** Hybrid (concolic)  
**Language scope:** C (DART); Windows native binaries (SAGE)  
**Benchmarks:** Windows file parsers; industrial applications  
**Metrics:** Code coverage, crash/bug discovery rate  
**Limitations:** Constraint solving bottleneck; path explosion; language-specific instrumentation.  
**SBG delta:** SBG focuses on behavioral equivalence across versions and languages, not adversarial input generation.

---

### [10] Nethercote & Seward — Valgrind
**Citation:** Nethercote, N., Seward, J. "Valgrind: A Framework for Heavyweight Dynamic Binary Instrumentation." *PLDI*, 2007.  
**Year:** 2007  
**Problem:** General-purpose dynamic binary instrumentation framework for program analysis.  
**Representation:** VEX IR (lifted from native binary); tool plug-ins (Memcheck, Callgrind, etc.)  
**Analysis type:** Dynamic (binary instrumentation)  
**Language scope:** Language-agnostic at binary level (Linux x86/x64/ARM)  
**Benchmarks:** SPEC CPU2000, custom memory-error benchmarks  
**Metrics:** Overhead (slowdown factor), error detection rate  
**Limitations:** High runtime overhead (10–50×). Cannot run on closed systems. No semantic behavior abstraction.  
**SBG delta:** SBG extracts semantic behavioral signatures, not just memory/performance profiles. Valgrind is a platform; SBG is a characterization system.

---

### [11] Luk et al. — Pin
**Citation:** Luk, C.-K., Cohn, R., Muth, R., Patil, H., Klauser, A., Lowney, G., Wallace, S., Reddi, V.J., Hazelwood, K. "Pin: Building Customized Program Analysis Tools with Dynamic Instrumentation." *PLDI*, 2005.  
**Year:** 2005  
**Problem:** A JIT-based dynamic instrumentation platform for x86.  
**Representation:** Instrumented x86 traces; Pintool API.  
**Analysis type:** Dynamic  
**Language scope:** Language-agnostic (compiled to x86)  
**Benchmarks:** SPEC CPU2000; various analysis tools  
**Metrics:** Instrumentation overhead; tool expressiveness  
**Limitations:** x86/x64 only; no abstraction over semantics; tool must be written in C++.  
**SBG delta:** SBG works at a higher semantic level and targets multi-language source-level analysis.

## Domain 4 — Semantic Similarity

### [12] Gabel & Su — Scalable Code Clone Detection
**Citation:** Gabel, M., Su, Z. "A Study of the Uniqueness of Source Code." *FSE*, 2010.  
**Year:** 2010  
**Problem:** How unique is source code? Characterizes clone density in large corpora.  
**Representation:** 6-token sliding windows; suffix array for exact matching.  
**Analysis type:** Static  
**Language scope:** Multi-language (C, Java, Python in corpus)  
**Benchmarks:** 6,000 open-source projects (~430 MLOC)  
**Metrics:** Fraction of unique vs. duplicated code windows  
**Limitations:** Token-level only; no semantic understanding; misses semantic clones (Type-4).  
**SBG delta:** SBG targets behavioral (Type-4) similarity — two programs that compute the same thing in different ways — which token-level approaches miss by design.

---

### [13] Jiang et al. — DECKARD
**Citation:** Jiang, L., Misherghi, G., Su, Z., Glondu, S. "DECKARD: Scalable and Accurate Tree-based Detection of Code Clones." *ICSE*, 2007.  
**Year:** 2007  
**Problem:** Scalable AST-based clone detection using tree-structure feature vectors.  
**Representation:** Characteristic vectors of AST subtrees; LSH for approximate nearest neighbor.  
**Analysis type:** Static  
**Language scope:** C, Java (parser-dependent)  
**Benchmarks:** Linux kernel, SPEC CPU  
**Metrics:** Recall/precision vs. manual oracle; scalability  
**Limitations:** Misses semantic clones; language-specific parser required; structural transformations fool it.  
**SBG delta:** SBG's behavioral genome is parser-independent and captures semantic equivalence regardless of syntactic form.

---

### [14] White et al. — Deep Learning for Code Clone Detection
**Citation:** White, M., Tufano, M., Vendome, C., Poshyvanyk, D. "Deep Learning Code Fragments for Code Clone Detection." *ASE*, 2016.  
**Year:** 2016  
**Problem:** Learn token-level and abstract syntax embeddings for clone detection with RNNs.  
**Representation:** Token sequences + AST paths fed into RNN/LSTM.  
**Analysis type:** Static  
**Language scope:** Java  
**Benchmarks:** BigCloneBench, OJ Clone  
**Metrics:** Precision, recall, F1; false positive rate  
**Limitations:** Java-only; semantic clones still difficult; requires large labeled training data.  
**SBG delta:** SBG does not require labeled clone pairs; behavioral similarity emerges from execution characterization.

---

### [15] Feng et al. — Scalable Graph-based Bug Search (Asm2Vec successor)
**Citation:** Feng, Q., Zhou, R., Xu, C., Cheng, Y., Testa, B., Yin, H. "Scalable Graph-based Bug Search for Firmware Images." *CCS*, 2016.  
**Year:** 2016  
**Problem:** Bug search in firmware by matching CFG subgraphs at scale.  
**Representation:** Attributed CFG; random-walk graph kernel.  
**Analysis type:** Static  
**Language scope:** ARM/MIPS firmware binaries  
**Benchmarks:** 33 routers' firmware images, known CVEs  
**Metrics:** Recall@1/5/10, query time  
**Limitations:** Graph kernel is approximate; no semantic execution behavior.  
**SBG delta:** SBG captures runtime behavioral semantics; firmware without OS instrumentation points is outside its current target but conceptually addressable.

## Domain 5 — Program Equivalence

### [16] Godlin & Strichman — Regression Verification
**Citation:** Godlin, B., Strichman, O. "Regression Verification." *DAC*, 2009.  
**Year:** 2009  
**Problem:** Formally verify that a new program version is semantically equivalent to the old one.  
**Representation:** Mutual summaries (loop invariants) proved equivalent via SMT.  
**Analysis type:** Static (formal)  
**Language scope:** C (loops, procedures)  
**Benchmarks:** Small C programs; industrial case studies  
**Metrics:** Proof success rate, analysis time  
**Limitations:** Only sound for loops with computable summaries. Does not scale to large programs or complex data structures. Requires matching program structure.  
**SBG delta:** SBG uses dynamic behavioral fingerprints rather than formal proofs; it scales to real-world software where proof-based methods stall. SBG trades soundness for scalability, honestly.

---

### [17] Churchill et al. — Sound Loop Summarization
**Citation:** Churchill, B., Sharma, R., Bastien, J.-B., Aiken, A. "Sound Loop Summarization and Regression Verification." *PLDI*, 2019.  
**Year:** 2019  
**Problem:** Sound regression verification for loops using abstract interpretation.  
**Representation:** Abstract loop summaries; relational invariants between old/new version.  
**Analysis type:** Static (abstract interpretation)  
**Language scope:** C  
**Benchmarks:** LibPNG transformation case studies  
**Metrics:** Soundness (proof of equivalence or divergence found)  
**Limitations:** Restricted to numeric loops; cannot handle pointer aliasing, strings, or complex heap structures.  
**SBG delta:** SBG operates on arbitrary programs including those with complex data structures; it is not sound but practically useful on the full software corpus.

---

### [18] Partush & Yahav — Abstract Semantic Differencing
**Citation:** Partush, N., Yahav, E. "Abstract Semantic Differencing for Numerical Programs." *SAS*, 2013.  
**Year:** 2013  
**Problem:** Compute behavioral diff between two versions of a numerical C program using abstract interpretation.  
**Representation:** Abstract states (polyhedra, intervals) jointly propagated for old and new program.  
**Analysis type:** Static  
**Language scope:** C (numerical subset)  
**Benchmarks:** LibPNG, hand-crafted examples  
**Metrics:** Precision of detected semantic differences  
**Limitations:** Strictly numerical domains; heap, strings, I/O not handled.  
**SBG delta:** SBG does not restrict to numerical programs; it observes behavioral differences across the full value domain via execution.

---

### [19] Lahiri et al. — SYMDIFF
**Citation:** Lahiri, S.K., Hawblitzel, C., Kawaguchi, M., Rebêlo, H. "SYMDIFF: A Language-Agnostic Semantic Diff Tool for Imperative Programs." *CAV*, 2012.  
**Year:** 2012  
**Problem:** Semantic diff of two program versions using symbolic execution and verification conditions.  
**Representation:** Verification conditions over pairs of program paths; Z3 solver.  
**Analysis type:** Static (symbolic)  
**Language scope:** C, Boogie (language-agnostic via Boogie IR)  
**Benchmarks:** Windows device drivers; LibPNG  
**Metrics:** True semantic differences found; analysis time  
**Limitations:** Limited to straight-line code regions between matched function pairs; solver scalability.  
**SBG delta:** SBG does not require matched function pairs and does not invoke an SMT solver; it extracts behavioral fingerprints from traces directly.

---

## Domain 6 — Code Embeddings

### [20] Alon et al. — code2vec
**Citation:** Alon, U., Zilberstein, M., Levy, O., Yahav, E. "code2vec: Learning Distributed Representations of Code." *POPL*, 2019.  
**Year:** 2019  
**Problem:** Learn a distributed vector representation for code snippets from AST paths.  
**Representation:** Bag of AST path-contexts; attention-weighted aggregation → dense vector.  
**Analysis type:** Static  
**Language scope:** Java (trained); transferable with retraining  
**Benchmarks:** 14M Java methods from GitHub  
**Metrics:** F1 on method name prediction  
**Limitations:** AST-path representation is syntax-dependent; does not capture runtime behavior; variable semantics require retraining.  
**SBG delta:** SBG embeddings incorporate dynamic execution context; code2vec produces static embeddings that two semantically identical but syntactically different programs may map far apart.

---

### [21] Feng et al. — code2seq
**Citation:** Feng, Z., Guo, D., Tang, D., Duan, N., Feng, X., Gong, M., Shou, L., Qin, B., Liu, T., Jiang, D., Zhou, M. "CodeBERT: A Pre-Trained Model for Programming and Natural Languages." *EMNLP*, 2020. (Referencing the code2seq predecessor: Alon, U. et al., *ICLR*, 2019.)  
**Year:** 2019  
**Problem:** Generate code summaries from AST sequence paths.  
**Representation:** LSTM over AST path sequences (encoder-decoder).  
**Analysis type:** Static  
**Language scope:** Java, C#  
**Benchmarks:** Java-small, Java-med, Java-large; C# corpora  
**Metrics:** BLEU, F1 on token-level predictions  
**Limitations:** Sequence-only; no runtime information; limited to trained languages.  
**SBG delta:** SBG does not generate natural-language summaries; it produces behavioral fingerprints grounded in execution.

---

### [22] Feng et al. — CodeBERT
**Citation:** Feng, Z., Guo, D., Tang, D., et al. "CodeBERT: A Pre-Trained Model for Programming and Natural Languages." *EMNLP Findings*, 2020.  
**Year:** 2020  
**Problem:** Pre-train a bimodal transformer model over code and docstrings.  
**Representation:** Transformer (RoBERTa-style) over token sequences; bimodal NL+PL.  
**Analysis type:** Static  
**Language scope:** 6 PL (Python, Java, JS, PHP, Ruby, Go)  
**Benchmarks:** CodeSearchNet (6 languages); code-to-NL retrieval  
**Metrics:** MRR on code search; BLEU on code summarization  
**Limitations:** Token-level representation; runtime behavior invisible; fine-tuning required for downstream tasks.  
**SBG delta:** SBG's behavioral genome cannot be derived from static token distributions; two programs with identical tokens but different runtime semantics would be indistinguishable to CodeBERT.

---

### [23] Guo et al. — GraphCodeBERT
**Citation:** Guo, D., Ren, S., Lu, S., Guo, Z., Liu, S., Jiang, D., ... Zhou, M. "GraphCodeBERT: Pre-training Code Representations with Data Flow." *ICLR*, 2021.  
**Year:** 2021  
**Problem:** Enrich CodeBERT with data-flow graphs to capture variable relationships.  
**Representation:** Transformer over tokens + data-flow edges (which-variable-comes-from-which).  
**Analysis type:** Static  
**Language scope:** Same 6-language CodeSearchNet corpus  
**Benchmarks:** CodeSearchNet; clone detection (BigCloneBench); code translation  
**Metrics:** MRR, F1, BLEU  
**Limitations:** Data flow is still a static approximation; does not capture actual values or runtime paths.  
**SBG delta:** SBG captures actual runtime value flows, not statically approximated ones; this matters for programs whose data flow is input-dependent.

## Domain 7 — Regression Detection

### [24] Nilsson & Offutt — Regression Test Selection
**Citation:** Nilsson, R., Offutt, J., Mellin, J. "Test Case Minimization for Mutation Testing of Feature Models." *(see also)* Rothermel, G., Harrold, M.J. "Analyzing Regression Test Selection Techniques." *IEEE TSE*, 1996.  
**Year:** 1996  
**Problem:** Select a subset of existing tests sufficient to detect regressions in modified code.  
**Representation:** Control/data-flow graphs; change impact analysis on edges.  
**Analysis type:** Static (with dynamic test execution)  
**Language scope:** C, Java (tool-dependent)  
**Benchmarks:** Siemens test suite; hand-crafted subject programs  
**Metrics:** Inclusion rate (tests selected), fault detection rate  
**Limitations:** Safe but not minimal; requires test suite; no notion of behavioral fingerprinting.  
**SBG delta:** SBG detects behavioral regressions without a pre-existing test suite, using behavioral signature divergence directly.

---

### [25] Kim et al. — Automatic Test Amplification
**Citation:** Kim, J., Zimmermann, T., DeLine, R., Begel, A. "Data Scientists in Software Teams: State of the Practice and Challenges." *(contrast with)* Baudry, B., Allier, S., Monperrus, M. "Tailored Source Code Transformations to Synthesize Computationally Diverse Program Variants." *ISSTA*, 2014.  
**Year:** 2014  
**Problem:** Amplify existing unit tests to increase behavioral coverage of variants.  
**Representation:** Existing test executions + source code mutation.  
**Analysis type:** Hybrid  
**Language scope:** Java  
**Benchmarks:** Apache Commons, Defects4J  
**Metrics:** Mutation score, coverage improvement  
**Limitations:** Requires existing tests; limited to Java; amplification may produce equivalent mutants.  
**SBG delta:** SBG operates without requiring an initial test suite and focuses on behavioral genome divergence as the primary signal.

---

### [26] Cioroaica et al. — Behavioral Regression Testing for Component Composition
**Citation:** Cioroaica, E., Chren, S., Buhnova, B. "Behavioral Regression Testing in Component-based Systems." *SEAA*, 2018.  
**Year:** 2018  
**Problem:** Detect regression in composed component systems when a component is upgraded.  
**Representation:** I/O contracts at component interfaces; test oracles from previous runs.  
**Analysis type:** Dynamic  
**Language scope:** Component-model agnostic (Java-based case study)  
**Benchmarks:** Smart home system case study  
**Metrics:** Detected regressions vs. manual oracle  
**Limitations:** Interface-level only; does not inspect internal behavioral change; small scale.  
**SBG delta:** SBG captures full intra-procedural and inter-procedural behavioral fingerprints, not just interface I/O contracts.

## Domain 8 — Mutation Testing

### [27] Jia & Harman — Mutation Testing Survey
**Citation:** Jia, Y., Harman, M. "An Analysis and Survey of the Development of Mutation Testing." *IEEE TSE*, 2011.  
**Year:** 2011  
**Problem:** Survey of mutation testing operators, tools, and applications.  
**Representation:** Syntactic source code mutations (operators: AOR, ROR, COR, etc.).  
**Analysis type:** Static mutation + dynamic test execution  
**Language scope:** C, Java, Fortran (historically diverse)  
**Benchmarks:** Siemens suite; historical literature  
**Metrics:** Mutation score; equivalent mutant rate  
**Limitations:** Equivalent mutants are undecidable; mutation score can be saturated without functional correctness.  
**SBG delta:** SBG does not enumerate syntactic mutations; it characterizes the behavioral effect of any change, including semantics-preserving refactors that mutation testing cannot distinguish.

---

### [28] Just et al. — Defects4J
**Citation:** Just, R., Jalali, D., Ernst, M.D. "Defects4J: A Database of Existing Faults to Enable Controlled Testing Studies in Java." *ISSTA*, 2014.  
**Year:** 2014  
**Problem:** Provide a reproducible benchmark of real Java bugs for testing research.  
**Representation:** 395 real bugs from 5 Java projects with triggering tests.  
**Analysis type:** Static (benchmark construction)  
**Language scope:** Java  
**Benchmarks:** Self (Defects4J is the benchmark)  
**Metrics:** Number of bugs, projects, triggering tests  
**Limitations:** Java-only; does not characterize the behavioral difference caused by each bug.  
**SBG delta:** SBG could annotate Defects4J bugs with precise behavioral genome divergence signatures — a potential downstream use case.

---

### [29] Papadakis et al. — Pitest (PITest mutation tool)
**Citation:** Coles, H., Laurent, T., Henard, C., Papadakis, M., Ventresque, A. "PIT: A Practical Mutation Testing Tool for Java." *ICST*, 2016.  
**Year:** 2016  
**Problem:** Industrial-strength bytecode-level mutation testing for Java.  
**Representation:** Bytecode mutations applied to .class files.  
**Analysis type:** Hybrid (static mutation + dynamic test execution)  
**Language scope:** Java (JVM bytecode)  
**Benchmarks:** Apache Commons, Spring Framework  
**Metrics:** Mutation score; execution time  
**Limitations:** JVM only; mutation operators may miss semantic-level bugs; equivalent mutant problem unresolved.  
**SBG delta:** SBG is not restricted to JVM and captures semantic behavioral divergence rather than syntactic mutation coverage.

## Domain 9 — Program Dependence

### [30] Ferrante et al. — Program Dependence Graph
**Citation:** Ferrante, J., Ottenstein, K.J., Warren, J.D. "The Program Dependence Graph and Its Use in Optimization." *ACM TOPLAS*, 1987.  
**Year:** 1987  
**Problem:** Represent data and control dependencies for program optimization and slicing.  
**Representation:** PDG: nodes = statements, edges = data/control dependence.  
**Analysis type:** Static  
**Language scope:** General (formalized; implemented for FORTRAN/C)  
**Benchmarks:** Theoretical; benchmark programs of the era  
**Metrics:** Optimization effectiveness (code size, speed)  
**Limitations:** Static; does not capture runtime value flows; approximated for pointer-heavy code.  
**SBG delta:** SBG augments static dependence with dynamic value propagation to build behavioral genomes that static PDGs cannot express.

---

### [31] Reps et al. — Interprocedural Slicing
**Citation:** Reps, T., Horwitz, S., Sagiv, M. "Precise Interprocedural Dataflow Analysis via Graph Reachability." *POPL*, 1995.  
**Year:** 1995  
**Problem:** Precise interprocedural data-flow analysis using IFDS/IDE frameworks.  
**Representation:** Exploded supergraph; context-sensitive reachability.  
**Analysis type:** Static  
**Language scope:** General (formalized; implemented for C)  
**Benchmarks:** Case studies from software maintenance  
**Metrics:** Precision vs. call-string approach; asymptotic complexity  
**Limitations:** May-alias approximation limits precision; exponential in general; no runtime information.  
**SBG delta:** SBG uses dynamic traces for precise (not approximated) value propagation, avoiding alias analysis imprecision.

---

### [32] Horwitz et al. — System Dependence Graph
**Citation:** Horwitz, S., Reps, T., Binkley, D. "Interprocedural Slicing Using Dependence Graphs." *TOPLAS*, 1990.  
**Year:** 1990  
**Problem:** Extend PDG to interprocedural context for program slicing.  
**Representation:** System Dependence Graph (SDG): procedure-level PDGs connected by call/return edges.  
**Analysis type:** Static  
**Language scope:** General  
**Benchmarks:** Case studies  
**Metrics:** Correctness of slices  
**Limitations:** Call-by-reference aliasing unsound in C; no dynamic information.  
**SBG delta:** SBG does not require a static dependence graph; runtime traces directly encode which values actually depend on which.

## Domain 10 — Cross-Language Program Analysis

### [33] Buch & Trivedi — Code2vec Cross-Language
**Citation:** Buch, L., Trivedi, A. "Learning Program Semantics with Code Representations: An Empirical Study." *SANER*, 2019.  
**Year:** 2019  
**Problem:** Empirically compare static code representations across languages for semantic tasks.  
**Representation:** AST paths, CFG, PDG embeddings; cross-language comparison.  
**Analysis type:** Static  
**Language scope:** Java, Python, C  
**Benchmarks:** Algorithm classification tasks (OJ dataset)  
**Metrics:** Classification accuracy  
**Limitations:** Semantic equivalence is approximated by same-algorithm label; no runtime verification.  
**SBG delta:** SBG does not rely on algorithm-level labels; behavioral equivalence is established from execution, making it label-free.

---

### [34] Perez et al. — Cross-Language Clone Detection (CLCDSA)
**Citation:** Perez, A., Cerny, T., Vitek, J. "Cross-Language Program Classification via Tree Kernels." *(see also)* Nafi, K.W., Kar, T.S., Roy, B., Roy, C.K., Schneider, K.A. "CLCDSA: Cross Language Code Clone Detection using Syntactic Features and API Documentation." *ASE*, 2019.  
**Year:** 2019  
**Problem:** Detect code clones across different programming languages.  
**Representation:** Syntactic feature vectors + API documentation similarity.

## COVERAGE GAPS

The following areas are identified as having **no substantial prior work** that addresses the problem from SBG's angle. These represent genuine research opportunities.

### CG-1 — Longitudinal Behavioral Genome Tracking
No prior work builds a **versioned behavioral genome** — a structured, queryable record of how a program's full behavioral profile evolves across every release over its entire lifetime. Existing regression tools compare pairs of versions; no system maintains a cumulative genome database.

### CG-2 — Cross-Language Behavioral Equivalence Without Compilation
No work establishes behavioral equivalence between programs written in fundamentally different paradigms (e.g., Python vs. Rust vs. Clojure) **without requiring a common IR** (LLVM, JVM). All cross-language similarity work relies on a shared compilation target or surface-level lexical similarity.

### CG-3 — Behavioral Genome as a Software Supply-Chain Artifact
No prior work treats a **behavioral signature as a first-class supply-chain artifact** analogous to an SBOM (Software Bill of Materials). Existing SBOMs record component provenance, not behavioral characteristics.

### CG-4 — Unsupervised Behavioral Anomaly Detection Without Test Suites
Regression detection tools universally require either (a) a test suite, or (b) a formal specification. No work detects behavioral regression purely from **unlabeled execution traces** using unsupervised anomaly detection over behavioral embeddings.

### CG-5 — Multi-Modal Behavioral Fingerprinting (Source + Binary + Runtime)
No single framework jointly fingerprints a program at the source level, binary level, and runtime level and correlates all three into a single behavioral identity. Works treat these modalities in isolation.

### CG-6 — Behavioral Diff as a Developer-Facing Review Artifact
No tool produces a **human-readable behavioral diff** suitable for inclusion in a code review (analogous to a syntactic diff) that precisely identifies what changed in program behavior, not just what changed in code structure.

### CG-7 — Behavioral Genome Across Operating Environments
No work characterizes how the **same binary's behavior diverges** across operating system versions, hardware architectures, and library versions in a unified behavioral genome model.

### [41] Piech et al. 2015 — Learning Program Embeddings to Propagate Feedback on Student Code

| Field | Value |
|-------|-------|
| **Citation** | Piech, C., Huang, J., Nguyen, A., Phulsuksombati, M., Sahami, M., Guibas, L. "Learning Program Embeddings to Propagate Feedback on Student Code." ICML 2015. |

| **Static/Dynamic** | Dynamic (execution-grounded) |

| **State?** | Partial (variable values at execution points — similar to SBG STATE genome) |
| **Language agnostic?** | No (Python/Java, requires test suite) |
| **Regression?** | No (student program clustering, not version-pair comparison) |
| **Benchmark?** | Yes (student code corpus, not publicly available) |

### [42] Sumner et al. 2011 — Precise Execution Comparison for Regression Detection

| Field | Value |
|-------|-------|
| **Citation** | Sumner, N., Zheng, Y., Bhansali, S., Zhang, X. "Comparative analysis of software behavioral traces." ICST 2011. Also: Sumner, N. and Zhang, X. "Precise Calling Context Encoding." IEEE TOSEM. |
| **Problem** | Detect behavioral regressions between two versions of a program |
| **Representation** | Lossless execution trace comparison with dynamic slicing and hash-based alignment |
| **Static/Dynamic** | Dynamic (full trace capture) |
| **Temporal?** | Yes (full sequence preserved — not compressed) |
| **State?** | Yes (heap state tracked at key points) |
| **Language agnostic?** | No (C/LLVM instrumentation) |
| **Regression?** | Yes (primary use case: regression detection between C program versions) |
| **Benchmark?** | Small (6 C programs, not publicly available) |
| **Key difference from SBG** | Sumner uses LOSSLESS trace comparison (exact sequence matching with hashing) requiring O(trace_length) space. SBG uses LOSSY compression into an 8-dimensional feature vector with O(1) space per genome. Sumner requires identical execution environments (same OS, same inputs); SBG is designed for cross-language comparison where traces cannot be aligned exactly. Sumner provides exact equivalence/difference verdict (binary); SBG provides a graded distance in [0,1] for ranking. Sumner cannot scale to programs with long traces (memory bound); SBG is constant-space after extraction. The core architectural choice of SBG (lossy but portable compression) is a direct design response to the lossless comparison approach: SBG trades precision for portability and scalability. |

**Why SBG is still novel vs Sumner:** SBG's primary contribution is the multi-language, multi-dimensional, formally-specified LOSSY behavioral representation. Sumner shows that lossless works; SBG investigates whether lossy compression can still preserve enough signal for semantic change detection — the answer (partially) and the conditions under which it works are the novel finding.
