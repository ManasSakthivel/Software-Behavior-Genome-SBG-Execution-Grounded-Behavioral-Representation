## 1. Output-Free Guarantee Definition

EEP (Extended Execution Profile) guarantees that no program output is consumed during behavioral comparison. Specifically, the following are NEVER read during EEP inference:

| Forbidden Signal | Status |
|-----------------|--------|
| Return values | ✗ NEVER consumed |
| stdout | ✗ NEVER consumed |
| stderr (except trace events) | ✗ NEVER consumed |
| Test pass/fail labels | ✗ NEVER consumed |
| Mutation/regression labels | ✗ NEVER consumed |
| Fixed-version expected outputs | ✗ NEVER consumed |
| Patch/diff contents | ✗ NEVER consumed |
| Exception message text | ✗ NEVER consumed (only exception TYPE occurrence) |
| Oracle/ground-truth labels during inference | ✗ NEVER consumed |

## 3. Java EEP — Output-Free Audit

**Instrumentation:** Method-boundary TRACE ENTER/EXIT/EXCEPTION on stderr  
**Output separation:** Java programs use `System.err.println` for traces; `System.out` carries functional output. These are captured by separate `subprocess` pipes (`stdout=PIPE`, `stderr=PIPE`). The trace parser reads ONLY stderr. stdout is captured and immediately discarded (never read, never stored).

| ID | Check | Mechanism | Result |
|----|-------|-----------|--------|
| OL-J-1 | Trace events go to stderr only | `System.err.println("TRACE ...")` in instrumented code | ✓ PASS |
| OL-J-2 | stdout discarded | `subprocess.run(..., capture_output=True)` — `result.stdout` never accessed | ✓ PASS |
| OL-J-3 | No return values emitted | Trace lines emit only method name and depth counter | ✓ PASS |
| OL-J-4 | Exception type recorded, not message | `_e.getClass().getSimpleName()` — class name only, no message | ✓ PASS |
| OL-J-5 | No field values in trace | ENTER/EXIT events carry only method name and depth integer | ✓ PASS |

**Code evidence:**
```java

System.err.println("TRACE ENTER gcd depth=" + _eepDepth);  // no values
```

## 4. Formal Output-Free Property

**Theorem (Output-Free Invariant):**  
Let A and B be two programs, I a set of inputs, and T(P, I) the execution trace of program P on inputs I (as produced by the EEP instrumentation layer). Then:

d_EEP(A, B) = f(T(A, I), T(B, I))

where f is a pure function of the trace structures and does not access:
- A(i) or B(i) for any input i ∈ I (the output values)
- Any ground-truth labels
- Any test oracle results

**Proof sketch:** Inspect `compute_eep_distance()` in `sbg/repair/execution_profile.py`. It accepts two `ExecutionProfile` objects. These objects contain only:
- `trace_lengths` (list of int counts)
- `line_seq_hashes` (MD5 of anonymized line index sequences)
- `call_depth_maxima` (list of ints)
- `exception_types` (list of exception class names or None)
- `sequential_drift` (float derived from hash comparison)
- `n_inputs` (count)

None of these fields contain output values. The `ExecutionProfile.extract()` method uses `sys.settrace` to count events and hash sequences — it calls `fn(arg)` and captures trace structure, discarding the return value. □

## 5. Trace-Preserving Invisibility Theorem

**Theorem 1 (Trace-Preserving Invisibility):**  
Let A and B be program versions where T(A, I) = T(B, I) for all inputs in set I. Then d_EEP(A, B) = 0.

*This is not a failure — it is a mathematical consequence of the output-free constraint.*

## 6. Known Non-Output-Free Limitation

**NC-CS-1:** Variable-rename invariance holds (0/9 false positives), but `for → while` refactoring produces EEP=0.153 > τ*=0.08.

This is NOT an output leakage issue. It is a CPython sys.settrace event granularity issue: Python's tracer emits different event sequences for `for` loops vs `while` loops with identical semantics. This is a **trace representation issue** (the representation is not invariant to this specific refactoring), not an output-free violation. The output-free guarantee is not compromised — the EEP is wrong (false positive) but not because it read an output.
